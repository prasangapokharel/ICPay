BUG #1: DOLR AI TOKEN MISSING icrc1_balance_of
===========================================
Severity: HIGH
Canister: 6rdgd-kyaaa-aaaaq-aaavq-cai (DOLR AI Token)
Type: ICRC-1 Standard Non-Compliance

Description:
The DOLR AI token canister supports ICRC-1, ICRC-2, ICRC-3, ICRC-10, ICRC-21, ICRC-103, ICRC-106 standards,
but is MISSING the required icrc1_balance_of query method. The ICRC-1 standard mandates that all token
ledgers expose icrc1_balance_of as a query method to allow anyone to check any account's balance.

Without this method:
- Wallets cannot display user token balances
- Token aggregators and indexers cannot track DOLR AI balances
- DEXes cannot validate user balances before trades
- Composability and standard compliance are broken
- Users may send tokens without being able to verify their own balances

Verified methods present:
  - icrc1_name: "DOLR AI" (PASS)
  - icrc1_symbol: "DOLR" (PASS)
  - icrc1_decimals: 8 (PASS)
  - icrc1_fee: 100,000 (PASS)
  - icrc1_total_supply: 108,321,227,737,328,246 (PASS)
  - icrc1_minting_account: 6wcax-haaaa-aaaaq-aaava-cai (PASS)
  - icrc1_transfer: (update) (PASS)
  - icrc1_balance_of: MISSING *** BUG ***
  - icrc1_supported_standards: ICRC-1,2,3,10,21,103,106 (PASS)
  - icrc1_metadata: full metadata (PASS)
  - icrc2_approve: (update) (PASS)
  - icrc2_allowance: (query) (PASS)
  - icrc3_get_blocks: (query) (PASS)
  - is_ledger_ready: (query) (PASS)

Reproduction:
  dfx canister call 6rdgd-kyaaa-aaaaq-aaavq-cai icrc1_balance_of --query \
    '(record{owner=principal"2vxsx-fae";subaccount=null})' --network ic
  Error: IC0536 'Canister has no query method icrc1_balance_of'

Fix: Implement icrc1_balance_of query method in the token canister's Rust/Motoko code.
The standard method signature is: icrc1_balance_of(account: Account) -> Tokens (query)

BUG #2: ICP LEDGER PANIC ON SEND_DFX CANDID PARSING
===========================================
Severity: MEDIUM
Canister: ryjl3-tyaaa-aaaaa-aaaba-cai (ICP Ledger)
Type: Error Handling / DoS Potential

Description:
The ICP Ledger's legacy send_dfx method panics with an unwrap().expect() on Candid deserialization
errors instead of gracefully handling malformed arguments. When called with improperly formatted
Candid arguments, the canister traps with:
"Panicked at 'called Result::unwrap() on an Err value: Custom(Trailing value after finishing deserialization)'"

This is a potential DoS vector - adversaries can cause the canister to trap repeatedly by
sending malformed arguments, consuming canister cycles unnecessarily.

Reproduction:
  dfx canister call ryjl3-tyaaa-aaaaa-aaaba-cai send_dfx '(record{...})' --network ic
  (with improperly formatted arguments)
  Result: IC0503 "Canister called ic0.trap with message: Panicked ..."

Note: The icrc1_transfer method handles deserialization errors more gracefully (returning Err variants).
The legacy send_dfx and transfer methods use unwrap() which causes panics instead of proper error handling.

Fix: Replace unwrap().expect() calls with proper Result handling in send_dfx and related legacy methods.

BUG #6: ICPCANISTER CALL CANDID INFERENCE WARNING
===========================================
Severity: INFO
Canisters: All canisters without a .did file
Type: Tooling / Developer Experience

Description:
When calling canister methods without a proper Candid interface definition, dfx falls back to
"inferred types" which may produce incorrect Candid serialization. This can lead to:
- "Trailing value after finishing deserialization" errors (ICP ledger)
- Method routing failures (query vs update)
- Incorrect argument encoding

All canisters in this audit were tested without explicit .did files, relying on dfx's
inferred type system.

Fix: Always publish .did files with canister deployments for proper type safety.

BUG #8: ICP Ledger No Memo Length Limit (Spam/Exfiltration Risk)
===========================================
Severity: LOW
Canister: ryjl3-tyaaa-aaaaa-aaaba-cai
Type: Data Integrity / Spam Risk

Description:
The ICP Ledger memo field accepts nat64 (max 2^64) with no length limit.
Unlike DOLR AI token which limits memos to 32 chars, the ICP Ledger
has no memo size restriction.

Potential issues:
1. Spam: Attackers could flood the ledger with large memo fields,
   increasing block sizes and slowing down the network
2. Data exfiltration: Memos are stored permanently on-chain and
   visible to all, making them unsuitable for sensitive data
3. Storage cost: Large memos increase archival storage requirements

Contrast: DOLR AI token limits memos to 32 characters (icrc1:max_memo_length: 32)
